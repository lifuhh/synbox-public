# Agent Notes

- **Never commit anything sensitive.** The repo is private (checked 2026-10-23). It was public earlier, so everything committed while it was public is already out, and anyone given access later sees every commit, commit message, branch, PR description and PR comment, which stay in history after they are deleted. Sensitive means:
  - secrets, API keys, tokens, cookies, `.env` contents, service-account files;
  - personal data: emails, real names of private people, account ids;
  - lyrics text and song audio (copyrighted; song titles and video ids are fine);
  - session transcripts;
  - open security weaknesses in production (for example storage or database permissions that are too open), until they are fixed;
  - internal details of any employer.

  Before every commit, read the staged diff and the message for these. Before every PR, read its description the same way. When unsure, leave it out and ask.

- **Everything committed here can go public.** `bun harness/public/export.ts` rebuilds the public copy (github.com/lifuhh/synbox-public) from `staging` with full history, minus `docs/log/`, `docs/private/` and `harness/public/`, and pushes only with `--push` once its checks pass (gitleaks, banned terms, uncleared Japanese lines). So code, comments and commit messages are written for a stranger: neutral, no quotes of the owner's messages (state the rule instead), no backend pipeline libraries, nothing about how the backend reaches YouTube. A failing check is fixed at its source or by a reviewed rule in `harness/public/`, never by pushing past it.

- **Every PR carries its change-log entry.** `docs/log/` is the project's history, committed since 2026-10-23: one entry per PR in the shape set by `docs/log/README.md`, written in the PR's own worktree and committed with the change, and corrected in the same PR if the change moves before merge. An entry carries no PR number: `bun harness/history.ts` reads it from the merge commit of the entry's `branch`, so nothing is committed after the PR opens. Tag it with `features:` slugs from `docs/log/FEATURES.md`. Before changing how something works, read that feature's history (`bun harness/history.ts feature <slug>`) or `grep -l <area or song id> docs/log/*`, so an earlier fix is not undone. Entries follow the sensitive-content list above: cite a video id and line number, never a lyric line.
- **Build the tool, not a one-off script.** When an investigation needs a script to read or change production data (a song's rows and versions, the library, logs, Appwrite, D1), and the same question will come up again, make it a harness or repo tool with arguments named for that job, documented here, instead of leaving it in a scratchpad (the owner's rule, 2026-10-24; examples: `services.lyrics.inspect`, `relabel`, `recommended --discovery`). Read-only by default; writes behind an explicit flag.
- Local reports and visual write-ups (HTML summaries, before/after screenshots, measurements) go in `.reports/YYYY-MM-DD-<slug>/`, one folder per report: an `index.html` with its images beside it, referenced by relative path so it opens offline. `.reports/` is gitignored; never commit a report. Anything worth keeping about why a change was made goes in the change log instead.

## UI and UX work: the better-* skills, every time

Any UI or UX change (a screen, component, dialog, layout, copy, colour, icon, motion or interaction) runs the `better-interface` skill and the `better-*` skills it routes to, alongside poteto-mode: once before designing and once as a review before the PR (the owner's rule, 2026-10-26; they should never have to ask). A subagent given UI work is told so in its prompt. The alignment rules below are part of that review.

- **User-facing copy** (the owner's rule, 2026-10-27; it covers `src/`, the Worker's messages and `index.html`): write every line a user reads by the `pstack:unslop` skill, with the fewest words that work and nothing the control already says.
  - One-line UI text ends without a full stop: descriptions, hints, notes, placeholders, empty states, menu secondary lines, toasts, badges and errors, also when it holds two short sentences ("Too long. Songs can be 1 to 8 minutes"). A question mark stays only on a real question. Prose pages (About's FAQ answers, Privacy, Terms) keep normal punctuation.
  - Nothing that reads as machine-written: "seamless", "effortless", "dive in", "journey", "elevate", "empower", "unlock", "delve", "embark", "feel free to", "don't hesitate", "we'd love to hear", "whether you're…", "in today's…", cheering exclamation marks, em-dash flourishes, lists of three adjectives.
  - Short labels at key positions (nav, buttons, pills, tabs, titles, column headers, status labels, accessible names of buttons) are Title Case; prose and tooltips are sentence case; identifier-like tokens (`iOS`) pass through as written.
- **Motion** (the owner's rule, 2026-10-27; every animated transition, a morph of one element into another above all):
  - Nothing teleports: no element jumps between frames, appears from nowhere or vanishes while still visible. It moves continuously, fades over at least two frames, or hands over in place to the element that takes its part (within 0.5px).
  - Scaling goes one way per transition: in a morph that shrinks nothing grows, in one that grows nothing shrinks, and nothing shrinks and then grows back.
  - It lands decisively: no edge passes where it lands and comes back (0.5px), no tail creeps the last pixels in, and a box's edges move on one shared progress (never one edge leading, so it never looks slanted).
  - Children stay attached to what they belong to: a button rides its field's end and text its field's edge, inside the box, never on a path of their own. A copy drawn in flight carries no CSS transition of its own (it would trail every move).
  - Every morph has a motion audit: a `Morph` in `harness/bench/probes/motion.ts` (selectors for its parts and the passes that drive it, slow and fast, both ways), registered in `harness/bench/suite.ts`, so `check` runs it frame by frame (`motion-hero-flight-*`). Its notes name each jump, and the frames behind them are in the run's `frames.json`.

## Phones, the installed app and desktop

The installed app (PWA) and the website are the same build: there is no phone code path to keep in sync. When they look different, the cause is one of two things, and every UI change must account for both:

- **The engine.** Every iPhone browser and the installed iOS app run WebKit; desktop is usually Chromium. The same CSS lays out differently. Known cases, each fixed once in `src/globals.css`:
  - Furigana: Chromium stands an `<rt>` on the kanji's line box, WebKit above the font's full ascent (0.34em higher). `lyric-ruby-text`'s negative margin puts both at the same spot.
  - Flex: an empty spacer with a `min-height` and no `flex-basis` gets its min-height as the basis in WebKit, so it grows past it. Spacers that share space (`anchor-spacer`, `lyrics-lift`) set `flex-basis: 0`.
  - iOS clips a `filter` on an inline box and paints no text-clipped background on `<rt>` (see `lyric-karaoke-line` and the karaoke fill spans); iOS keeps the last tapped element in `:hover`, so touch never reads `:hover`.
- **iOS versions.** Support the two latest major iOS versions: 26 and 27 now. Every iOS workaround says in its comment which versions it targets, the WebKit bug it answers, and how it is detected (a feature or behaviour check, such as `@supports`, `display-mode` or a measured value; sniff the user agent only when nothing else can tell, as the install guide does). A workaround whose bug is fixed in both supported versions is removed. The full inventory and what changed in Safari 27 are in the main checkout's `docs/private/2026-10-26-ios-26-27-workarounds.md`.
- **The screen class.** A phone on its side is wide (~850px) but only ~390px tall. A value keyed only to width (`cqw`, `width < 40rem`) sizes it like a monitor. Key phone rules to the device, not one axis: `touch:` (finger input), `short:` (phone on its side), `portrait:`, and cap width-based sizes by height (`min(2cqw, 4cqh)`). The same pixel gap or dock distance is a finger's width on a phone and nothing on a monitor: use a share of the space instead.

Rules for the player (and any full-screen surface):

- **The floating UI draws over the lyrics and never moves them.** The controls (plus, in portrait, the rail, and on a phone on its side the top bar) sit above the lyrics and may cover them; nothing in the lyrics' layout reads whether they show (the owner's rule, 2026-10-23). `--stage-chrome-h` is the bottom edge they cover while they show: a notice that must clear them reads it, only while they show. Never offset a layer permanently by an element that hides.
- **Presses outside a control go to the stage.** The stage's own taps (show/hide controls, double-tap seek) sit under everything. Don't widen a press target over it: the lyrics take presses only on their drawn text (`lyrics-hit-text`).
- **Input on the floating UI counts as activity.** Don't stop `pointerdown` on it, or the controls hide under a finger that is still tapping them.
- **Keep a dragged thing mounted, and save it on the drop**, not on every move: a remount mid-drag kills the drag, and a storage write per move is jank on a phone.
- **Act on release, inside the control** (`onClick`), never on the press: a press that slides off or turns into a scroll does nothing (the owner's rule, 2026-10-26; `docs/private/2026-10-26-activation-timing-research.md`). Only a mouse may open a menu on the press (press, drag, release picks an item), and direct manipulation (sliders, drags, swipes) starts on the press and carries `data-press-ok="<why>"`. Every layout audit presses each control to check it (`harness/bench/probes/press.ts`).

**Sheets, dialogs and panels** (from Apple's HIG, Material, NN/g, WCAG 2.2 and web.dev; the research with sources is the main checkout's `docs/private/2026-10-26-mobile-modal-research.md`, the owner's rule since 2026-10-26):

- Settings that change what's behind them as they're set (Lyrics Style, Text Style) go in a sheet that leaves it in view, undimmed: `DialogContent variant='sheet'` on touch, a popover with a mouse. A centred, dimming dialog is for what must be answered first (sign in, a confirmation, a form).
- The shape follows the space, not the device: a bottom sheet about half the screen high on a tall screen, a side sheet on a short one (`short:`, the Lock Landscape page included); one sheet at a time.
- Always a visible Close at the top; swipe, Back, Escape and a tap outside are extra ways out.
- Every press target is at least 44×44px on touch, whatever its drawn size; adjacent targets keep at least 8px apart.
- Fewer buttons first: before adding one, make an existing control carry the meaning (Lyrics Style's All Songs | This Song is the scope _and_ the reset), and show an action only when it can do something (Reset Positions only while something moved). One prominent button per view at most, never a destructive one; a remaining action is quiet text sized to its words, placed with the setting it acts on, never a full-width filled button and never a wrapped grid of buttons.
- Prefer Undo to a confirmation for anything reversible (`offerUndo`); confirm only what can't be undone, with buttons that name the outcome.
- A control acts on release inside it (`onClick`): press, slide off, release does nothing, and a press that becomes a scroll does nothing. Only direct manipulation (a slider, a drag) starts on press; no `onPointerDown`/`onMouseDown` actions.
- Controls in a sheet stay out of the safe areas (`--safe-*`); its surface may run under them.

**"All views"** means three views, defined once in `harness/bench/engines/browser.ts` › `ALL_VIEWS`: **web** (desktop Chromium 1440×900), **PWA portrait** (WebKit iPhone 390×844, installed) and **PWA landscape** (WebKit 844×390, installed), each phone view with the iPhone's safe areas injected and the installed app emulated through `navigator.standalone`.

**Check every UI change in all views**, by measuring, not only by looking:

- `bun harness/views.ts <path-or-url>` opens one page in all views, runs the layout audit on each, prints every too-small, covered, cut-off or inset-trapped press target, anything painted inside a safe-area inset, a sideways pan, a text field iOS would zoom into and clipped text, each with its box, and writes `.reports/YYYY-MM-DD-views-<slug>/index.html` with the three screenshots side by side. `--compare <base-url|git-ref>` (`origin/staging`, `https://synbox.io`) makes it one before/after row per view; `--port N` looks at a server already running (`wt serve`) instead of a fresh production build. `--state <name>` opens one of the page's UI states first (`search-button`, `library`, `controls`: `harness/bench/probes/layout.ts` › `OPENED_STATES`).
- `bun harness/bench/cli.ts check --only layout-<page>` (page names: `bun harness/bench/cli.ts list`) runs the same audit for every route in all views, plus iPhone Safari (`safari-portrait`; `safari-landscape` on home, gallery, player and search; `safari-narrow` at 320px wide), at rest and with each UI state a user opens there (the top bar's search and menus, the Search page typed into, the player's controls and Lyrics Style, the reader's Text Style). Besides layout it counts controls with no accessible name, scrolling boxes a keyboard can't reach, and smooth scrolling under Reduce Motion. `check` runs those of the pages a change reaches, `check --full` all of them. A UI change that adds something a user opens (a menu, a sheet, an overlay) adds its state to `OPENED_STATES`, in its own PR like any evaluator change.

- An iPhone on its side reaches the full-screen player two ways: Full Screen with the rotation lock on turns the page by CSS (`html[data-landscape-lock]`), and with it off iOS rotates the screen. They must look the same (the owner's rule, 2026-10-27): `check` › `landscape-parity` compares their boxes within 1px, in Zoom and Fit, and checks the side bands are black and no control sits in a safe area.

A new route with parameters needs a sample URL in `harness/routes.json`, in the same PR; elements marked `data-bench` are the audits' hooks, so keep the attribute on whatever replaces them. Chrome's device mode is not a substitute (it flips back to `pointer: fine` mid-page and is not WebKit). Report the measurements; show the `views` page only when the user asks, or for a big restructure or a new feature (screenshots cost tokens). Keep every driven browser silent: open every browser through `harness/bench/engines/browser.ts` › `open`, which silences every frame (`engines/silence.ts`, WebKit has no mute flag) — never launch Playwright directly (a test fails if harness code does) — and never press Tap to Unmute (hide the pill with injected CSS if it spoils a shot). Real-device feel (touch drag, home indicator, status bar) still needs the user's phone: say what was not checked.

**Measure alignment, every time** (the owner's standing rule). Run the `better-*` skills (`better-interface` covers all of them) over every page a change touches, and measure with the browser, not by eye:

- an icon beside a label or a number (a tab, a pill, a count) is centred on the control's vertical centre and on the text's centre line, within 1px; a lone icon is centred in its button both ways;
- items in a row share one centre line (or one baseline for text), and a list's rows start at one left edge;
- a dropdown is `src/components/ui/select.tsx` › `Select`, never a bare `<select>`: the browser's own arrow ignores padding and radius and sits in a pill's curve;
- report the measured offsets with the screenshots. An off-centre glyph that is optically right (a play triangle) is the only exception, and says so.

## The owner's asks

Every message the owner types in `~/github-workspace`, mid-task ones included, lands in a private inbox (global hook `~/.claude/hooks/capture-asks.py`). `bun harness/asks.ts` files them as asks and tracks each one to its PR, so none is dropped (`harness/README.md` › "Asks").

- **When the owner sends a message:** `bun harness/asks.ts triage`, then file each new message: `new "<the ask>" --from <key> --project <p>`, `link <id> <key>` (a follow-up), or `skip <key>` (not an ask).
- **As work lands:** `bun harness/asks.ts set <id> in_progress|done --pr fe#<n>` (`be#<n>` for the backend). Work that must wait is `set <id> deferred --blocker "<what holds it>" --unblocked-by <condition>`. When a condition comes true (a release, a Worker deploy), run `bun harness/asks.ts cleared <condition>`: its asks reopen and it prints them.
- **Every final report ends with `bun harness/asks.ts report`'s output**, so deferred and open asks stay in front of the owner.

## Owner steps

Anything only the owner can do (a setting in a web portal, a check on their phone, a payment) goes into `docs/private/owner-steps.md` in the main checkout the moment it's found, never only into a chat reply. It's private because portal paths name project ids. Each step has the same shape: **when** (what must happen first), **portal** (the URL and which project or account), **where** (the menu path), **set** (exact values), **check** (how to see it worked), and the ask it belongs to. The owner shouldn't have to ask for steps; asks.ts's `report` lists the open ones in every final report, and the step-by-step goes in the reply too when a step becomes doable. When the owner confirms one, move it to Done with the date. Something an agent can run itself (a deploy, a migration, a secret it was given) is not an owner step: ask, then run it.

## Shipping a change

Finished work collects in one long-lived branch, `staging`, and reaches production only through `bun harness/release.ts`, one merge to `main` for everything in staging. Every merge to `main` is a Netlify build, which spends the account's monthly build minutes; staging costs none. The global PR hook enforces this: it blocks a PR into `main`, a merge into `main` and a push to `main` from anything but the release script.

1. **Start in your own worktree**, never in the main checkout (other sessions work there): `bun harness/wt.ts start <type>/<slug> --session <session name>` (from anywhere in the repo), type one of `feat` `fix` `chore` `docs` `perf`. It fetches, adds `../synbox-<slug>` on a new branch from `origin/staging`, records who owns it so other sessions can reach you (Claude Code: your name is the first line of `ListAgents`), and installs the app's and the auth Worker's packages. One task, one worktree, one branch, one PR.
2. **Run it.** In the worktree, `bun harness/wt.ts serve`, as a background task: it takes the first free port from 5173 and prints the address. Stop it by stopping that task, never by killing a process by name or port (other sessions' servers and browsers run beside yours). Run probes and other one-off scripts in the foreground with a timeout, so nothing is left to kill. The dev server reads the main checkout's env file (`envDir` in `vite.config.ts`); don't copy it into the worktree. On ports other than 5173 the page and lyrics work but `/api/youtube` gets 403, because the local YouTube key only allows known localhost referrers. Karaoke timing calls the local backend (`VITE_SYNBOX_BE_URL`) and fails while it isn't running.
3. **Check, scoped to the change:** commit, then `bun harness/bench/cli.ts check` in the worktree, and look at the change itself in a real browser.
   - It always runs typecheck, lint, tests, format, the build and the size budgets. Of the browser audits it runs only those the branch's diff against staging can reach, through the real import graph: a page's audits when anything that page imports changed; every page's when the shell changed (`src/globals.css`, the root layout, the top bar, shared `ui/` components, `index.html`, `public/`, `vite.config.ts`, packages), except the timing audits whose `scope.shell` says they don't observe that part of it; a probe's audits when its probe changed. A module whose change alters only some exports reaches only the modules that import those (`harness/README.md` › Scope). It prints what it ran and why, and the verdict records it. `bun harness/bench/cli.ts scope` shows the selection without running anything.
   - A commit that changes only docs (`docs/`, Markdown outside `src/` and `public/`) after a passing `check` reuses its verdict in seconds.
   - Checks from several sessions run at the same time: browser audits share the machine through slots, and only timing audits (lyric shifts, motion) take it to themselves, so don't wait for another session's check.
   - `--only <audit prefix>` while working (no verdict; names: `bun harness/bench/cli.ts list`). `--full` runs every audit; `release.ts` runs it on staging's combined tree before anything goes live, so what a scoped check can't see is still checked once per release.
   - A failing audit is read before anything is rerun (the owner's rule, 2026-10-27): its notes and, for a timing audit, the run's `frames.json` say what moved, by how much and where. Then it is one of three, and the PR and log entry say which, with that evidence:
     - **your change caused it** (any harness or shared-code change can reach an audit the scope didn't name): fix it;
     - **staging is broken**: report it with the evidence and file it as an ask (`bun harness/asks.ts new`), so its owner fixes it;
     - **the audit is unreliable** (the same tree passes and fails, e.g. under machine load): file it as an ask with what varied between runs, so the audit is made reliable. Only then rerun, once, to confirm the classification. Never rerun until it passes. The harness's own retry of an audit that produced nothing (a page that never got ready) is the exception: it measured nothing, so it is run again and says so.

   Staging holds only finished work: anything merged there can go live at the next release, from any session.

4. **Commit, push, open the PR into staging and merge it yourself, without asking:** read the staged diff and the PR body against the rules above, `gh pr create --base staging`, then `gh pr merge <n> --merge`. Nothing deploys. Work that isn't finished stays on its branch.
5. **When the user's request is done, ask one question, the only one about shipping.** Run `bun harness/release.ts --dry-run`, which lists everything in staging (every session's, not only yours). Then ask with AskUserQuestion: "Ship staging to live now?", the list in the question with the deferred and open asks from `bun harness/asks.ts report`, options **Ship Now** and **Leave in Staging**. Skip the question when staging has nothing to ship.
   - **Ship Now**, or the user saying ship, deploy, release or merge at any time: `bun harness/release.ts`. It takes a lock, so only one release runs on the machine. It runs the full check (`check --full`, every audit) on staging's combined tree (about eight minutes on a busy machine), then the smoke test on a local production build of staging served by Netlify's own runtime here (`harness/smoke.ts --local`, about 45 seconds, no build minutes: local smoke first, always), opens the PR staging → main, builds a deploy preview of staging and runs the flow smoke test on it (`harness/smoke.ts`: the main user flows against the real backends, read-only, in all views, about 40 seconds), merges, waits until https://synbox.io serves the merge, and runs the smoke test there too. Netlify build minutes are scarce: `--no-preview` skips the deploy preview once the local smoke passed (1 build instead of 2); keep the preview for a change only a real deploy shows (Netlify UI variables, caching, HTTPS) or a phone check. It stops before merging on a failing check, a failing local smoke, a preview that fails to build or a failing smoke; fix it in a PR into staging and run it again. A smoke FAIL on the live site prints a loud warning with how to roll back: tell the user at once. After it, `bun harness/asks.ts cleared frontend-released`.
   - **Leave in Staging**: the session is done. The work ships with the next release.
   - **The user must try it on a phone first:** `bun harness/release.ts --preview` builds one deploy preview of staging, smoke-tests it and prints its link with the verdict. Hand the user the link; ship when they say so. `bun harness/smoke.ts <url>` runs the smoke test alone on any deployed copy.
6. **Clean up** after the merge into staging: stop your `serve` task, then `bun harness/wt.ts finish <slug>`. It copies the worktree's `.reports/` into the main checkout's, removes the worktree and deletes the branch. It refuses, and says why, while there are uncommitted changes, the branch is not in staging, or its dev server still runs; never force past it (`--force`, `-D`, `rm -rf`).

This repo is the frontend only. The backend (`synbox-transcribe-whisper`) ships the same way, with its own staging branch and `python3 harness/release.py` (Cloud Run); merging here never deploys it. A request that changed both repos still asks one question, listing both stagings; Ship Now runs both releases, the backend's first when the frontend depends on it.

## Resolving conflicts

- **Rebase, don't merge `staging` in:** `git fetch origin && git rebase origin/staging`, then `git push --force-with-lease`. The PR that merges second does the rebasing.
- **Learn what the other side meant before editing a hunk.** `git log origin/staging -p -- <file>` gives the commit; `gh pr list --state merged --search <sha>` gives its PR; read the PR description and its log entry. Keep both intents, with merged `staging` as the baseline you adapt to. Then rerun the checks and look at both changes in the browser, not just yours.
- **When the other side is unmerged work in another worktree and the intents clash, ask its session.** `git worktree list` maps the branch to its worktree; `cat "$(git -C <worktree> rev-parse --path-format=absolute --git-dir)/agent-session"` names the session; `ListAgents` shows whether it is still alive. `SendMessage` it the files, both intents, your proposed resolution and who rebases, then wait for its answer. Silence is not agreement. Never ask a peer to do something your own session was refused.
- **If the owner is gone or never answers**, resolve from its PR description and log entry. Ask the user only when the two intents are opposite product decisions.
